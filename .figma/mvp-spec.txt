47: 1.   Executive Summary
48: 
49: BoostX is a guest-checkout social media marketing (SMM) panel. A customer chooses a platform and service,
50: enters a target link or username, pays by mobile money, uploads a payment screenshot, and receives an
51: AI-verified spendable balance in Ghana Cedis (GHS). The order is then submitted to a fulfillment provider
52: through a REST API, and the customer tracks delivery in real time — no account or password required.
53: 
54: This document restructures the original BoostX specification into an implementation-ready build guide. It
55: covers the customer journey, system architecture, database schema, the pricing engine, the
56: fulfillment-provider integration (boostcenter2.com/api/v2), payment verification, security requirements, and a
57: phased MVP build plan.
58: 
59: Scope of this revision
60: 
61: Pricing Currency is GHS only. Customer price = provider cost (converted to GHS) + a flat
62: GHS 5.00 markup, applied once per order.
63: 
64: Provider API Confirmed live against boostcenter2.com/api/v2 — a standard action-based SMM
65: provider API (services, add, status, refill, cancel, balance).
66: 
67: Accounts Registration and login are new and optional. Customers and admins sign in on
68: one shared page with no visible admin path; registering lets a customer track
69: delivery status and full order history.
70: 
71: Reliability BoostX does not promise zero issues — no honest system can. Section 12
72: indexes the specific failure modes it does defend against (double orders, provider
73: failure, race conditions, fake screenshots) and names the gap that still needs
74: pre-launch testing against the live provider.

76: 2.   The Five Non-Negotiable Rules
77: 
78: Rule 1 — Platform scope
79: 
80: Only five platforms: TikTok, Instagram, Facebook, X, Telegram. No others are shown to customers,
81: regardless of what the provider catalog offers — confirmed against a live reference storefront
82: (baloonboost.com/order), which lists nine (also Spotify, Audiomack, Threads, YouTube). BoostX deliberately
83: shows five, not whatever the provider happens to support.
84: 
85: Rule 2 — Accounts are optional, never required
86: 
87: A customer can place an order as a guest, exactly as before. Registering is offered so they can track delivery
88: status and order history, but nothing behind checkout is gated on having an account.
89: 
90: Rule 3 — AI-assisted verification
91: 
92: Payment screenshots are checked automatically by an AI verification service before any balance is credited.
93: 
94: Rule 4 — Spend only what is verified
95: 
96: A customer can never spend more than the amount successfully verified and credited to their BoostX balance.
97: 
98: Rule 5 — Backend is the authority
99: 
100: Price, payment, balance, and order validation are decided by the backend. The frontend is for display only
101: and is never trusted.

107: 3.   Customer Journey
108: 
109: End-to-end flow a first-time customer follows. An account is never required to order — registering only adds
110: order tracking on top of the same flow:
111: 
112: 1.  Visit BoostX and select New Order — no sign-in prompt at this stage.
113: 
114: 2.  Select a platform (TikTok, Instagram, Facebook, X, or Telegram).
115: 
116: 3.  Select a service (e.g. TikTok Followers).
117: 
118: 4.  Enter the target link or username.
119: 
120: 5.  Enter quantity — BoostX shows a live price preview in GHS.
121: 
122: 6.  Pay the exact displayed amount via mobile money.
123: 
124: 7.  Upload a screenshot of the successful payment.
125: 
126: 8.  The AI verification service inspects the screenshot and confirms amount, recipient, status, and reference.
127: 
128: 9.  On success, the verified amount is credited to the customer's balance (guest session, or account if signed
129: in).
130: 
131: 10.  The customer confirms the order; the backend re-checks balance and reserves the charge.
132: 
133: 11.  BoostX submits the order to the provider API and stores the returned provider order ID.
134: 
135: 12.  The customer tracks status (Pending → In Progress → Completed) using their BoostX order ID — or, if
136: they register or sign in (Section 4), automatically inside their order history.
137: 
138: A guest who registers afterward doesn't lose their order history — see "Guest order claiming" in Section 4.

140: 4.   Accounts & Authentication
141: 
142: Customers can now register and log in to track deliveries and order history. Two rules shape everything in this
143: section: accounts are optional (Rule 2), and customer accounts and admin accounts are never told apart
144: anywhere the browser can see.
145: 
146: One shared login page
147: 
148: Customers and admins sign in through the exact same page, the exact same form (identifier + password), and
149: the exact same API endpoint —  POST /api/auth/login. There is no "Admin login" link, tab, toggle, or
150: hidden query parameter anywhere on the public site. The only place a login is ever treated differently is after
151: the password check succeeds, when the backend looks up that account's role column and decides where to
152: send the browser next.
153: 
154: Outcome What the browser is told
155: 
156: Customer credentials, correct Redirected to /account/orders. No mention of role in the response.
157: 
158: Admin credentials, correct Redirected to /admin. Same response shape as the customer case.
159: 
160: Wrong password "Incorrect email/phone or password." — identical wording either way.
161: 
162: Account doesn't exist at all The exact same "Incorrect email/phone or password." message — so
163: the page can't be used to check which emails have accounts.
164: 
165: Account temporarily locked Also the exact same generic message, so a locked-out attacker can't
166: tell they found a real account and just need to wait.
167:

171: 
172: Registration creates customers only
173: 
174: POST /api/auth/register hardcodes the new account's role to customer — there is no field, header, or
175: parameter on that endpoint that can produce an admin account. Admin accounts are created exclusively by a
176: separate function that is never wired to a public route: either a one-time seed script, or an internal endpoint
177: that itself requires an already-authenticated admin session to call.
178: 
179: Login security (this matters more here than usual)
180: 
181: •  Passwords are hashed (PBKDF2/bcrypt) — never stored or logged in plain text.
182: 
183: •  5 failed attempts locks the account for 15 minutes; the lockout is invisible to the person trying — they still
184: just see the generic error.
185: 
186: •  Session/role state is issued server-side as a signed token or server session; the browser can never edit its
187: own role by tampering with a cookie or request body.
188: 
189: •  Rate limiting applies to the login endpoint itself, independent of the per-account lockout, since this one
190: endpoint is also the admin's front door.
191: 
192: Guest order claiming
193: 
194: Guest checkout is unchanged (Section 7 keeps the guest_sessions table). When someone who already
195: ordered as a guest later registers — or logs in — with the same phone number or email they used at
196: checkout, BoostX automatically re-attaches those past orders to the new account, so order history doesn't
197: start from zero. This only matches the contact details the person just typed into the form in front of them; it
198: never scans for or pulls in anyone else's orders.

255: 5.   System Architecture
256: 
257: BoostX is a three-tier system: a frontend for guest ordering, a backend that owns all business rules, and a
258: PostgreSQL database as the single source of truth for money and orders.
259: 
260: Customer
261:   -> BoostX Frontend (Next.js / React)
262:      -> BoostX Backend API (FastAPI or Flask)
263:         -> Pricing Engine        (GHS pricing, flat markup)
264:         -> Payment Verification  (AI vision + business rules)
265:         -> Ledger Service        (append-only balance history)
266:         -> Order Service         (validation, reservation)
267:         -> Provider Adapter      (boostcenter2.com/api/v2)
268:         -> Admin Service
269:      -> PostgreSQL  (orders, payments, ledger, services)
270:      -> Redis + background worker  (status sync, refills, cleanup)
271:   -> SMM Provider API  (fulfillment)
272:   -> AI Vision Service  (payment screenshot analysis)
273: 
274: Component responsibilities
275: 
276: Component Owns Never does
277: 
278: Frontend UI, forms, price preview, file upload,
279: theme, tracking display Never holds provider API keys, admin
280: secrets, or the final price/balance
281: authority
282: 
283: Backend API All validation: service, target, quantity,
284: price, balance, order Never trusts a price, balance, or
285: service ID sent from the browser
286: 
287: Pricing Engine Converts provider USD cost to GHS and
288: applies the flat markup Never exposes the provider's
289: wholesale rate to the customer
290: 
291: Provider Adapter Talks to boostcenter2.com/api/v2 only Never lets a provider error reach the
292: customer unfiltered
293: 
294: Background Worker Service sync, order-status polling, refills,
295: session cleanup Never makes the customer wait on a
296: live provider round-trip

393: 8.   Pricing Engine — GHS Only
394: 
395: BoostX prices exclusively in Ghana Cedis. The provider's USD cost is converted to GHS and a flat markup of
396: GHS 5.00 is added once per order — not per unit, and not as a percentage. The formula:
397: 
398: customer_price_ghs =
399:     (provider_rate_usd_per_1000 / 1000 * quantity * usd_to_ghs_rate)
400:     + flat_markup_ghs   # default GHS 5.00
401: 
402: Worked example
403: 
404: Input Value
405: 
406: Provider service TikTok Followers (provider service ID 1)
407: 
408: Provider rate $0.90 per 1,000
409: 
410: Quantity ordered 1,000
411: 
412: USD → GHS rate (admin-configured) 10.70
413: 
414: Provider cost in GHS GHS 9.63
415: 
416: Flat markup + GHS 5.00
417: 
418: Customer price shown GHS 14.63
419: 
420: Rules enforced by the pricing engine
421: 
422: •  Runs server-side only. Any price shown by the frontend is a preview; the backend recalculates before
423: charging.
424: 
425: •  The provider's wholesale USD rate is never returned to the customer — only the final GHS price.
426: 
427: •  Quantity is validated against the service's provider-defined minimum/maximum before a quote is produced.
428: 
429: •  Money values use fixed-point Decimal arithmetic, rounded half-up to 2 decimal places — never floating
430: point.

435: 
436: USD → GHS exchange rate
437: 
438: The USD/GHS rate is volatile — quotes checked across multiple sources in the same week ranged from
439: roughly GHS 10.70 to GHS 15.18 per USD. This rate must be an admin-configurable setting (or refreshed
440: automatically from a live FX feed on a schedule), never hardcoded. A stale rate silently erodes margin or
441: overcharges customers.

506: Operational rules
507: 
508: •  The provider API key lives only in a server-side environment variable — never in frontend code.
509: 
510: •  Every provider call has a timeout and a small number of retries for network failures; provider-returned
511: business errors (e.g. an invalid order ID) are not retried.
512: 
513: •  The service catalog is synced periodically by a background worker into PostgreSQL — the
514: customer-facing dropdown never calls the provider live, keeping the site fast and within the provider's rate
515: limits.
516: 
517: •  Order-status polling for pending orders should run on a schedule (roughly every 1–5 minutes, tuned to the
518: provider's limits), not on every page load.

655: 11.   Order Lifecycle & Money Safety
656: 
657: Final order validation (on "Confirm Order")
658: 
659: 1.  Retrieve the service and confirm it is active
660: 
661: 2.  Verify the platform is enabled
662: 
663: 3.  Validate the target format
664: 
665: 4.  Validate quantity against min/max
666: 
667: 5.  Retrieve the current selling price from the pricing engine
668: 
669: 6.  Retrieve the customer's verified ledger balance
670:

672: 
673: 8.  Reserve/deduct the amount atomically
674: 
675: 9.  Submit the order to the provider
676: 
677: 10.  Save the returned provider order ID

679: 11.  Create the BoostX order record

683: If any step fails, reserved money is restored to the customer's balance. Money is never lost between
684: reservation and provider confirmation.

686: Anti-race-condition rule
687: 
688: Example: balance GHS 50. Two browser tabs each submit a GHS 40 order at the same moment. The
689: database transaction must lock/check the balance atomically so only one order can succeed — the balance
690: must never go negative.

693:

716: 12.   Reliability Principle — What BoostX Defends
717: Against
718: 
719: No real system can honestly guarantee zero issues — a provider will time out, a screenshot will be blurry, a
720: customer will double-click. BoostX's design goal is narrower and achievable: common failures should never
721: cost the customer their money or leave an order in an undefined state. The table below is a single index
722: of where that promise is actually enforced elsewhere in this document — nothing here is new behavior, it is a
723: deliberate summary of it.
724:

727: Customer double-clicks

729: is created; repeats return the original order. Section 11

732: was reserved The reserved amount is released back to the customer's
733: balance; the failure is logged as an event. Section 11
734:

736: same instant The balance check and deduction are atomic — only
737: one order can succeed; the balance never goes
738: negative.

857: 
858: Never trusted from the browser
859: 
860: price  ·  quantity  ·  service ID  ·  balance  ·  role — the backend always re-derives these itself.
861: 
862: Secrets — server-side only, never in frontend code

875: File upload security
876: 
877: •  Accept image formats only (PNG, JPG, JPEG, WEBP); enforce a maximum file size.
878: 
879: •  Never use the customer's original filename as a storage path.
880: 
881: •  Rename internally, e.g. /payments/2026/09/BX-PAY-839201-randomid.webp.
882: 
883: •  Store outside publicly executable paths, with controlled access.
884: 
885: Platform-wide controls
886: 
887: •  HTTPS everywhere; secure, expiring sessions
888: 
889: •  CSRF protection where applicable
890: 
891: •  Rate limiting on payment upload, order creation, order tracking, the shared login endpoint, and AI
892: verification
893: 
894: •  Input validation and file-type/size validation on every upload
895: 
896: •  SQL injection protection via parameterized queries / ORM
897: 
898: •  Audit logs for every admin action; request logging with no secrets in logs
899: 
900: •  Idempotency keys on order creation; unique constraint on transaction references
901: 
902: Shared login page hardening
903: 
904: •  Identical error message for wrong password, unknown account, and locked account — no enumeration.
905: 
906: •  Account lockout after 5 failed attempts (15 minutes) — enforced per account, not just per IP.
907: 
908: •  Passwords hashed with PBKDF2/bcrypt; never logged, never returned in any API response.
909: 
910: •  Role is read from the database after authentication, never accepted as input from the client.
911: 
912: •  Registration can only ever produce a customer account; admin accounts require an already-authenticated
913: admin.

1008: 
1009: Section 9 confirms the shape of boostcenter2.com/api/v2 — the actions, parameters, and response fields.

1014: within a sane min/max.
1015:

1017: provider order ID, status transitions, and final delivery all match what the customer sees.

1020: provider service supports both, regardless of what the catalog flag says.
